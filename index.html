SELECT & FROM

The two clauses you use in every single SQL query.

The concept

SELECT tells SQL which columns you want to see. FROM tells SQL which table to look in. That's it. Every query starts here.

SELECT column_name, another_column
FROM table_name;

To get everything from a table, use * (star):

SELECT *
FROM rides;
The table you're working with

Going further — aliases, DISTINCT, and expressions

Use AS to rename a column in the output — useful when a name is unclear or you're computing something new.

SELECT duration_minutes AS length_mins
FROM rides;

DISTINCT removes duplicate rows from the result — handy when you just want the unique set of values in a column.

SELECT DISTINCT city
FROM rides;

You can also compute new values directly in SELECT, not just pull raw columns:

SELECT ride_id, duration_minutes / 60.0 AS duration_hours
FROM rides;

duration_minutes / 60.0 divides each row's minutes by 60 to get hours, and AS duration_hours names that calculated result in the output — the underlying table is untouched, this only affects what you see back.

WHERE

Filter which rows you get back.

The concept

WHERE filters rows before anything else happens. Only rows that match the condition come through.

SELECT *
FROM rides
WHERE city = 'London';

Common operators: =   !=   >   <   >=   <=

Combine conditions with AND / OR:

SELECT *
FROM rides
WHERE city = 'London' AND duration_minutes > 20;

With AND, both conditions have to be true for a row to survive — a Manchester ride is excluded even if it's over 20 minutes, and a 5-minute London ride is excluded too. Only rides that are both in London and over 20 minutes come back.

Practice — write the query

Write a query that returns all columns for rides in Manchester.

SELECT * FROM rides WHERE city = 'Manchester'
Practice — write the query

Write a query that returns all columns for London rides with a duration greater than 10 minutes.

SELECT * FROM rides WHERE city = 'London' AND duration_minutes > 10
More filtering tools

BETWEEN checks a range (inclusive on both ends). IN checks against a list of values instead of chaining OR. LIKE matches text patterns with % as a wildcard. IS NULL / IS NOT NULL checks for missing values — never use = NULL, it silently matches nothing.

WHERE duration_minutes BETWEEN 10 AND 20
WHERE city IN ('London', 'Manchester')
WHERE city LIKE 'Lon%'
WHERE bike_id IS NOT NULL

When mixing AND and OR, use parentheses — AND binds tighter than OR, so without them the logic can silently mean something different from what you intended.

-- means: London rides, OR any ride over 30 minutes (probably not what you wanted)
WHERE city = 'London' AND duration_minutes > 10 OR duration_minutes > 30

-- means: London rides over 10 minutes, OR anything over 30 minutes — use parens to be explicit
WHERE (city = 'London' AND duration_minutes > 10) OR duration_minutes > 30

Practice — write the query

"WHERE filters rows. You decide which rows survive before anything else runs."
Date logic — comparing dates and DATEDIFF

Dates work like any other value in WHERE — write them as 'YYYY-MM-DD' and compare with the same operators: >, <, BETWEEN. "Basic date logic" mostly just means: is this date before/after that one, or within a range.

WHERE opened_date >= '2026-06-01'
WHERE opened_date BETWEEN '2026-06-01' AND '2026-06-30'

The other piece you need cold is turning two dates into a number of days — e.g. "how long did this take?" That's DATEDIFF. The exact syntax differs by SQL dialect, so know the idea more than one memorized spelling:

-- MySQL: DATEDIFF(later_date, earlier_date) — most common in these prep tools
DATEDIFF(closed_date, opened_date) AS days_to_close

-- Postgres/SQLite: just subtract the dates directly
closed_date - opened_date AS days_to_close

Whichever spelling comes up on the day, say the logic out loud first — "later minus earlier gives me days elapsed" — the interviewer cares more that you reasoned it than that you recalled the exact function name.

Table for this section — a tickets table, one row per support ticket:

ticket_idopened_dateclosed_date

T0022026-06-022026-06-02
T0032026-06-032026-06-10
T0042026-06-05

Notice T004 has no closed_date — it's still open. DATEDIFF against a NULL returns NULL rather than erroring, which is worth flagging out loud if you spot it: "this ticket's still open, so its days-to-close will come back blank."

GROUP BY & Aggregates

Collapse rows into groups and calculate something about each group.

The concept

Aggregate functions do a calculation across multiple rows: COUNT, SUM, AVG, MAX, MIN.

GROUP BY collapses rows with the same value into one row, then runs the aggregate on each group.

SELECT station_id, COUNT(ride_id) AS total_rides
FROM rides
GROUP BY station_id;

The AS keyword gives your calculated column a name you can reference later.

-- Result:
-- station_id | total_rides
-- ST01 | 2
-- ST02 | 2
-- ST03 | 1
"GROUP BY is how you answer 'how many per X' or 'average Y per X' questions. Every column in SELECT must either be in GROUP BY or inside an aggregate function."
Practice — write the query

Write a query that shows each station_id and the average duration_minutes for rides at that station. Name the average column avg_duration.

SELECT station_id, AVG(duration_minutes) AS avg_duration FROM rides GROUP BY station_id
Practice — write the query

Write a query that shows each city and the total number of rides in that city, named ride_count.

SELECT city, COUNT(ride_id) AS ride_count FROM rides GROUP BY city
Going further — conditional aggregation

You can put a CASE expression inside an aggregate to count or sum only rows that meet a condition — without needing a separate query per condition. This pattern shows up constantly in real analytics work (e.g. "how many orders were late" alongside "how many orders total", in one row).

SELECT station_id,
  COUNT(DISTINCT bike_id) AS unique_bikes,
  SUM(CASE WHEN duration_minutes > 20 THEN 1 ELSE 0 END) AS long_rides
FROM rides
GROUP BY station_id;

The CASE expression turns each row into a 1 or a 0 — 1 if its duration is over 20 minutes, 0 otherwise — and SUM adds those up per station, giving a count of just the "long" rides. It's really COUNT with a condition attached, done without a second query. COUNT(DISTINCT column) in the same SELECT counts unique values only, instead of every row.

HAVING

Filter groups after GROUP BY. The most commonly confused clause.

The concept

WHERE filters rows before grouping. HAVING filters groups after grouping. You cannot use WHERE to filter on an aggregate — that's what HAVING is for.

-- WRONG — can't use WHERE on an aggregate
SELECT station_id, COUNT(ride_id) AS total_rides
FROM rides
GROUP BY station_id
WHERE total_rides > 1; -- ❌ error
-- CORRECT — use HAVING to filter groups
SELECT station_id, COUNT(ride_id) AS total_rides
FROM rides
GROUP BY station_id
HAVING COUNT(ride_id) > 1; -- ✓
"WHERE = filter rows. HAVING = filter groups. If you're filtering on something you calculated with COUNT, SUM, or AVG — it's HAVING."
Practice — write the query

Write a query that shows only the stations with more than 1 ride, using COUNT and HAVING. Show station_id and total_rides.

SELECT station_id, COUNT(ride_id) AS total_rides FROM rides GROUP BY station_id HAVING COUNT(ride_id) > 1
Practice — write the query

Write a query that shows only the bikes with more than 1 ride, using COUNT and HAVING. Show bike_id and total_rides.

SELECT bike_id, COUNT(ride_id) AS total_rides FROM rides GROUP BY bike_id HAVING COUNT(ride_id) > 1
Using WHERE and HAVING together

A single query can use both — WHERE trims rows before grouping happens, HAVING trims the resulting groups. They're not interchangeable, and using both is common: filter out irrelevant rows early (cheaper), then filter the aggregated result.

SELECT station_id, COUNT(ride_id) AS total_rides
FROM rides
WHERE city = 'London'
GROUP BY station_id
HAVING COUNT(ride_id) > 1;

Walking through it in the order it actually runs: WHERE keeps only rows where city = 'London' — every other city is discarded before anything else happens. GROUP BY station_id then collapses the surviving London rows into one row per station. COUNT(ride_id) AS total_rides counts how many rows landed in each of those groups. Finally, HAVING COUNT(ride_id) > 1 throws out any station group whose count isn't above 1 — so a station with exactly one London ride never makes it into the result.

HAVING can also combine multiple aggregate conditions with AND/OR, just like WHERE does with row conditions.

Practice — write the query

Using WHERE and HAVING together, write a query that shows station_id and total_rides (COUNT) for London rides only, but only include stations with more than 1 ride.

SELECT station_id, COUNT(ride_id) AS total_rides FROM rides WHERE city = 'London' GROUP BY station_id HAVING COUNT(ride_id) > 1
Practice — write the query

SELECT city, AVG(duration_minutes) AS avg_duration FROM rides WHERE duration_minutes > 5 GROUP BY city HAVING AVG(duration_minutes) > 15

ORDER BY & LIMIT

Sort your results and cap how many rows come back.

The concept

ORDER BY sorts results. ASC = smallest first (default). DESC = largest first.

LIMIT caps the number of rows returned.

SELECT station_id, COUNT(ride_id) AS total_rides
FROM rides
GROUP BY station_id
ORDER BY total_rides DESC
LIMIT 3;

This returns the top 3 busiest stations.

Practice — write the query

Write a query that returns all rides ordered by duration_minutes from shortest to longest.

SELECT * FROM rides ORDER BY duration_minutes ASC
Practice — write the query

Write a query that returns the top 2 longest rides, showing ride_id and duration_minutes.

SELECT ride_id, duration_minutes FROM rides ORDER BY duration_minutes DESC LIMIT 2
"The full clause order: SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT. You don't need all of them, but they must appear in this order when you do."
Going further — multi-column sorts and OFFSET

ORDER BY can take multiple columns — the first breaks ties using the second, and so on.

ORDER BY city ASC, duration_minutes DESC

Rows are sorted by city first, A→Z. Only when two rows share the same city does duration_minutes come into play, breaking that tie longest-first.

OFFSET skips a number of rows before LIMIT starts counting — useful for pagination, or for questions like "the 2nd highest" instead of "the highest".

SELECT ride_id, duration_minutes
FROM rides
ORDER BY duration_minutes DESC
LIMIT 1 OFFSET 1; -- skips the top row, returns the 2nd-longest
Practice — write the query

SELECT ride_id, city, duration_minutes FROM rides ORDER BY city ASC, duration_minutes DESC
Practice — write the query

Write a query that skips the single longest ride and returns the next 2 longest. Show ride_id and duration_minutes.

INNER JOIN — only matching rows

FROM rides
LEFT JOIN stations ON rides.station_id = stations.station_id;

Returns all rides — even if no matching station exists. Missing station values show as NULL.

"INNER JOIN = only where both sides match. LEFT JOIN = everything from the left table, matched or not."
Practice — harder

Write a query that shows every station's station_name and how many rides started there, named ride_count — including stations with zero rides (like ST04). An INNER JOIN would silently drop ST04; you need a LEFT JOIN.

SELECT stations.station_name, COUNT(rides.ride_id) AS ride_count FROM stations LEFT JOIN rides ON stations.station_id = rides.station_id GROUP BY stations.station_name

Classic gotcha: use COUNT(rides.ride_id), not COUNT(*). COUNT(*) counts the row itself even when the join found nothing, so a zero-ride station would wrongly show 1.

Practice — write the query

Going further — other join types

RIGHT JOIN is the mirror of LEFT JOIN: everything from the right table, matched or not. FULL OUTER JOIN keeps everything from both sides, matched or not, filling in NULLs where there's no counterpart. Not every database supports RIGHT/FULL (SQLite added them recently; MySQL still doesn't do FULL) — when in doubt, a LEFT JOIN with the tables swapped does the same job as a RIGHT JOIN.

A self-join joins a table to itself — useful for comparing rows within the same table, like finding two rides from the same bike back-to-back. You just need to alias the table twice:

SELECT a.ride_id, b.ride_id
FROM rides a
JOIN rides b ON a.bike_id = b.bike_id AND a.ride_id < b.ride_id;

a and b are two aliases pointing at the same rides table, so the join is comparing rides against other rides. a.bike_id = b.bike_id pairs up rows that used the same bike. a.ride_id < b.ride_id is what makes it useful instead of noise — without it, every ride would also match itself (bike_id always equals its own bike_id), and every real pair would show up twice, once each direction.

Practice — write the query

Subqueries & CTEs

Use the result of one query inside another — and keep it readable.

Might come up, but almost anything you'd do here can also be solved with a JOIN or HAVING from the core lessons. Worth a skim, not worth drilling hard.

The concept

A subquery is a query nested inside another query. It can appear in WHERE (to compare against a calculated value), in FROM (to treat a query's result like a table), or in SELECT.

SELECT *
FROM rides
WHERE duration_minutes > (SELECT AVG(duration_minutes) FROM rides);

The inner query runs first, returns a single number, and the outer query compares each row's duration against it.

Practice — write the query

Write a query that returns the station_id and duration_minutes of rides where the duration is less than the average duration across all rides.

SELECT station_id, duration_minutes FROM rides WHERE duration_minutes < (SELECT AVG(duration_minutes) FROM rides)
Practice — write the query

Write a query that returns the ride_id and duration_minutes of the single ride with the longest duration, using a subquery in WHERE instead of ORDER BY/LIMIT.

SELECT ride_id, duration_minutes FROM rides WHERE duration_minutes = (SELECT MAX(duration_minutes) FROM rides)
CTEs — naming a subquery with WITH

A CTE (Common Table Expression) uses WITH ... AS (...) to give a subquery a name, then reference it like a table later in the same query. It doesn't change what's possible — it changes how readable a multi-step query is, which matters a lot once queries get complex.

WITH station_avg AS (
  SELECT station_id, AVG(duration_minutes) AS avg_duration
  FROM rides
  GROUP BY station_id
)
SELECT rides.ride_id, rides.duration_minutes, station_avg.avg_duration
FROM rides
JOIN station_avg ON rides.station_id = station_avg.station_id;

The WITH block runs first and is named station_avg — a table of one average duration per station. The outer query then joins rides to it on station_id, so each ride ends up sitting next to its own station's average, ready to compare against.

A correlated subquery is one that references a column from the outer query inside the inner query, so it re-runs once per outer row. They're powerful but slower — a CTE with a JOIN, like above, often does the same job more clearly.

"Reach for a subquery when you need one calculated value to filter against. Reach for a CTE when the query has more than one logical step — it reads top to bottom like a recipe instead of a nested puzzle."
Practice — write the query

Window Functions

Calculate across a group of rows without collapsing them into one.

This is a step up from what a technical-comprehension round tends to test. Only come here if the core six lessons and the decomposition framework already feel solid and you want extra depth.

The concept

GROUP BY collapses many rows into one row per group. A window function calculates something across a group of rows too — but keeps every row in the output. That's the core difference, and it's why window functions are everywhere in analytics: ranking, running totals, "top N per group", comparing a row to the one before it.

SELECT ride_id, station_id, duration_minutes,
  RANK() OVER (PARTITION BY station_id ORDER BY duration_minutes DESC) AS duration_rank
FROM rides;

PARTITION BY is like GROUP BY, but for the window — it resets the calculation for each group. ORDER BY inside OVER() controls the order the ranking (or running total) is calculated in.

Practice — write the query

Write a query that shows each ride's ride_id, station_id, and duration_minutes, plus its rank within its own station by duration (longest = 1). Name the column duration_rank and use RANK().

SELECT ride_id, station_id, duration_minutes, RANK() OVER (PARTITION BY station_id ORDER BY duration_minutes DESC) AS duration_rank FROM rides
Practice — write the query

Write a query that shows each ride's ride_id, city, and duration_minutes, plus its rank within its own city by duration (longest = 1), named duration_rank, using RANK().

SELECT ride_id, city, duration_minutes, RANK() OVER (PARTITION BY city ORDER BY duration_minutes DESC) AS duration_rank FROM rides
RANK vs DENSE_RANK vs ROW_NUMBER

ROW_NUMBER() always gives 1, 2, 3... with no ties. RANK() gives ties the same number, then skips (1, 2, 2, 4). DENSE_RANK() gives ties the same number without skipping (1, 2, 2, 3). LAG() / LEAD() pull a value from the previous / next row in the ordering — useful for comparing a row to what came before it.

"A window function can't be used directly in WHERE — it's calculated after WHERE and GROUP BY have already run. To filter on one (e.g. 'just the top row per group'), wrap it in a CTE or subquery first, then filter the outer query."

Bonus — unlikely to come up

UNION & Combining Multiple Sources

Stack results from separate queries — or separate systems — into one list.

A niche tool for a fit-round refresher. Read it if you're curious, but don't spend drilling time here — it's not part of the core set.

The concept

UNION stacks the results of two queries on top of each other, as long as they return the same number of columns in compatible types. UNION removes exact duplicate rows; UNION ALL keeps everything, including duplicates, and is faster since there's no dedup step — use it whenever you know duplicates can't happen, or don't care about them.

SELECT city FROM rides WHERE city = 'London'
UNION ALL
SELECT city FROM rides WHERE city = 'Manchester';

Each half is a complete query on its own — one returns the London rows' city values, the other returns the Manchester rows'. UNION ALL doesn't compare or join them; it just stacks the second query's rows underneath the first's, producing one combined column of city values instead of two separate result sets.

The real-world use case: your company runs on two systems that were never designed to talk to each other — an acquisition, a legacy system nobody's retired yet, a regional office with its own database. UNION lets you build one combined view without touching either source system.

Capstone: Two Systems, One Fulfillment Tool

This is the exact shape of the Palantir CodePair round — a messy real business problem, not a clean textbook question.

The decomposition thinking here matters far more than the UNION/CTE syntax it happens to use. If you're short on time, the standalone Decomposition Framework page covers the same reasoning without requiring the optional lessons.

The scenario

You work for Office Goods Corp, a paper and office goods company. Recently, your company acquired one of its competitors, Bureau SAS. The IT unification project won't start for another year, which means your colleagues are stuck tracking and managing orders on two different systems.

They've survived a couple of months by manually stitching spreadsheets together, but with demand growing, things have started to fall through the cracks: incorrect metrics, unfulfilled orders, unhappy customers. The fulfillment department has asked for help — something quick, ahead of the unification project.

After understanding the problem, you've decided to build a simple operational view that connects to both systems: one place for managers to see every order, spot what hasn't been assigned yet, and flag what's at risk of missing its delivery date. Along the way, it should end the debates about which spreadsheet is the most up to date.

Step 1 — unify the two systems

Build the base view: every order from both systems in one list, with order_id, customer, status, order_date, and a source_system column.

SELECT order_id, customer, status, order_date, 'Office Goods' AS source_system FROM orders_og UNION ALL SELECT order_id, customer, status, order_date, 'Bureau SAS' AS source_system FROM orders_bureau
Step 2 — normalize the statuses

orders_og's status is already clean. Write a query that combines both systems and produces a single status_clean column with only three values — Pending, Shipped, Delivered — for every order. Show order_id, customer, status_clean, and order_date.

SELECT order_id, customer, status AS status_clean, order_date FROM orders_og UNION ALL SELECT order_id, customer, CASE status WHEN 'awaiting' THEN 'Pending' WHEN 'dispatched' THEN 'Shipped' WHEN 'delivered' THEN 'Delivered' END AS status_clean, order_date FROM orders_bureau
Step 3 — find unassigned orders

Using a CTE named unified that combines order_id, customer, and order_date from both systems, write a query that returns every order with no matching row in assignments — the ones sitting unassigned right now.

WITH unified AS (SELECT order_id, customer, order_date FROM orders_og UNION ALL SELECT order_id, customer, order_date FROM orders_bureau) SELECT unified.order_id, unified.customer FROM unified LEFT JOIN assignments ON unified.order_id = assignments.order_id WHERE assignments.assigned_to IS NULL
Step 4 — flag at-risk deliveries

Assume today's date is 2026-07-01. Using a CTE named unified with the normalized status_clean and promised_date from both systems, write a query that returns every order that is not yet Delivered and whose promised_date has already passed. Show order_id, status_clean, and promised_date.

WITH unified AS (SELECT order_id, status AS status_clean, promised_date FROM orders_og UNION ALL SELECT order_id, CASE status WHEN 'awaiting' THEN 'Pending' WHEN 'dispatched' THEN 'Shipped' WHEN 'delivered' THEN 'Delivered' END AS status_clean, promised_date FROM orders_bureau) SELECT order_id, status_clean, promised_date FROM unified WHERE status_clean != 'Delivered' AND promised_date < '2026-07-01'

Decomposition round

Decomposition Framework

Turn a vague business ask into 2–4 concrete, data-answerable questions — before you touch SQL.

Why this matters

In the decomposition round, you won't get a clean SQL prompt. You'll get something like "a company reached out asking for help with X — how would you think about this?" The interviewer wants to see your framework before they hand you any tables. Show up with a repeatable process, not just SQL syntax, and you'll have somewhere to go the moment the ask feels vague.

The 5-step framework

1. Restate the goal, out loud. Say back what you think they're actually asking, in your own words, before doing anything else. If it's vague ("help us with X"), ask what decision this is meant to drive, or what "better" would look like.

2. Split the ask into 2–4 concrete sub-questions. A business ask is rarely one query's worth of work. Break it into pieces you could answer independently — e.g. "reduce late deliveries" becomes "which orders are late right now?", "where is it worst?", "is it getting worse over time?"

3. For each sub-question, name the data you'd need. Roughly which table, which columns, and what you'd filter/group/join on. You're not writing the query yet — just sketching what it would touch.

4. Start with the simplest version, then add complexity. Write the smallest query that gives a directional answer first. Refine after — joins, edge cases, date logic — once the simple version works.

5. Say what you assumed, and what you'd check next. Real data is messy — statuses spelled differently across systems, nulls that mean different things, definitions ("late," "active," "attrition") that vary by team. Call out anything you assumed — e.g. "assuming 'late' means past the promised date" — and what you'd validate if you had more time.

"A vague ask is not a query — it's 2 to 4 questions wearing a trenchcoat. Find them before you touch SQL."
Worked example

Ops leadership says: "Deliveries have been slipping lately — can you help us understand what's going on?"

1. Restate: They want to know why deliveries are late, and — more usefully — where to focus first. That means they'll want to know how bad it is, where it's concentrated, and whether it's trending worse.

2. Sub-questions: How many shipments are late right now? Which carriers or regions have the worst late-rate? Is the late-rate getting worse over recent weeks?

3. Data: A shipments table with a promised date and a delivered date. "Late" = delivered after the promised date, or not yet delivered and the promised date has already passed.

shipment_idcarrierregionpromised_datedelivered_datestatus
S001FastFreightNorth2026-06-202026-06-19Delivered
S002FastFreightNorth2026-06-212026-06-25Delivered
S003QuickHaulSouth2026-06-18In Transit
S004QuickHaulSouth2026-06-152026-06-22Delivered
S005FastFreightSouth2026-06-25In Transit

4. Simplest first: start with an overall count of late shipments, then break it out — this is exactly the shape of the practice query below.

-- simplest version: how many are late, full stop
SELECT COUNT(*) AS late_count
FROM shipments
WHERE (delivered_date IS NOT NULL AND delivered_date > promised_date)
  OR (delivered_date IS NULL AND promised_date < '2026-06-28');

The WHERE clause covers two different ways a shipment counts as late, joined by OR: the first parenthesized condition catches shipments that were delivered, but arrived after their promised_date; the second catches shipments still in transit (no delivered_date yet) whose promised_date has already slipped into the past. The parentheses matter here — without them, AND's tighter binding would change which rows qualify.

5. Assumptions to flag out loud: "in transit" past its promised date counts as late even though it hasn't technically failed to deliver yet — worth confirming that's what the business means by "late."

Practice — decompose it yourself

Finance says: "Customers keep disputing charges — can you dig into what's happening?" Before looking at any answer, write out your own breakdown: what's the real goal, what 2–4 sub-questions would you ask, and roughly what data would answer each one?

A possible breakdown — yours doesn't need to match, it just needs the same shape:

Restate: they want to understand disputes well enough to reduce them — likely looking for a pattern worth acting on.
Sub-questions: How many disputes are there, and what fraction of all transactions? Do disputes cluster by merchant, card type, or amount range? Is the dispute rate rising over time?
Data: probably a transactions table with a disputed flag, merchant, card_type, amount, and date — group by merchant/card_type, filter disputed = true, and look at a date trend.
Assumption to flag: whether "disputed" means opened or resolved-in-the-customer's-favor — those tell very different stories.
Practice — decompose it yourself, again

People ops says: "Attrition feels higher this quarter — can someone look into it?" Same drill: restate the goal, list 2–4 sub-questions, sketch the data each one needs. This one is deliberately vaguer than the last — the goal is to get fast at finding structure in an ask that has none yet.

A possible breakdown:

Restate: they want to know whether attrition is actually up, and if so, where it's concentrated, so they know where to focus retention efforts.
Sub-questions: What's this quarter's attrition rate compared to the last few quarters? Which teams, tenure bands, or managers show the highest attrition? Is it concentrated among a particular group (e.g. high performers, a specific tenure range)?
Data: an employees table with hire_date, termination_date, team, manager, and maybe performance_rating — compute a rate per period (departures / average headcount), group by team or tenure band, filter to terminations within the quarter.
Assumption to flag: does "attrition" mean voluntary departures only, or voluntary + involuntary combined? Those tell very different stories and change which rows you'd filter to.
Practice — now write the query

Using the shipments table above, and assuming today's date is 2026-06-28, write a query showing each carrier and how many of their shipments are currently late — delivered after the promised date, or not yet delivered with a promised date already in the past. Name the column late_count.

SELECT carrier, SUM(CASE WHEN (delivered_date IS NOT NULL AND delivered_date > promised_date) OR (delivered_date IS NULL AND promised_date < '2026-06-28') THEN 1 ELSE 0 END) AS late_count FROM shipments GROUP BY carrier

Clause order — always in this sequence
SELECT -- what columns
FROM -- which table
JOIN -- connect another table
WHERE -- filter rows (before grouping)
GROUP BY -- collapse into groups
HAVING -- filter groups (after grouping)
ORDER BY -- sort results
LIMIT -- cap number of rows
Aggregate functions
COUNT(column) -- number of rows
SUM(column) -- total
AVG(column) -- average
MAX(column) -- highest value
MIN(column) -- lowest value
WHERE vs HAVING
-- WHERE filters rows (use before GROUP BY)
WHERE city = 'London'

-- HAVING filters groups (use after GROUP BY)
HAVING COUNT(ride_id) > 5
Dates & DATEDIFF
-- comparisons work the same as any other value
WHERE opened_date >= '2026-06-01'

-- days between two dates — MySQL-style (most common here)
DATEDIFF(later_date, earlier_date)
-- Postgres/SQLite: just subtract — later_date - earlier_date
JOINs
-- INNER JOIN: only matching rows
FROM rides INNER JOIN stations
ON rides.station_id = stations.station_id

-- LEFT JOIN: all left rows, matched or not
FROM rides LEFT JOIN stations
ON rides.station_id = stations.station_id
